# Introduction {#introduction}

This chapter says what LiteEth is, why it exists, what it does and what it does not do. It ends with
the layout of the repository and a map of the manual. Every reader should start here.

## What the project is {#intro-what}

LiteEth connects an FPGA design to an Ethernet network. It frames the data, computes the checksums,
answers ARP and ping, and drives either a PHY chip on the board or the FPGA transceivers directly.
User logic sees streams of UDP payload, a Wishbone bus reachable over the network, or Ethernet
frames in memory for a CPU.

The project has four parts, shown in the figure below. The PHY moves bits between the MAC and the
external PHY or the SFP module. The MAC adds and checks the preamble and the CRC of each frame.

The ARP, IP, ICMP and UDP layers form the hardware stack, and the frontends give user logic
Etherbone or UDP streams; a PTP slave clock can run on top of UDP.

![LiteEth at a glance. User logic reaches the network through a frontend (Etherbone, UDP streamer,
raw UDP port); the hardware stack handles ARP, IP, ICMP and UDP; the MAC frames the data; the PHY
drives an external PHY chip or an SFP module.](intro_overview.svg)

The gateware is written in Python with Migen and LiteX, and generates Verilog for the FPGA tools. It
can be used as a LiteX library, usually through the `add_ethernet` and `add_etherbone` methods of a
LiteX SoC, or as a standalone Verilog core generated by `liteeth_gen` from a YAML configuration (see
[Integration](#integration)).

## Why LiteEth {#intro-why}

A network stack usually runs on a CPU. That is flexible but slow to start, hard to bound in latency,
and heavy for an FPGA that only needs to stream samples or expose a few registers.

LiteEth runs ARP, IP, ICMP and UDP in gateware: a design answers ping and moves UDP data with no CPU
at all.

The same stack runs on every PHY. The PHYs share one stream interface to the MAC, so moving a design
from a 100 Mbps MII board to a 10GBASE-R SFP+ port changes the PHY, its clocking and the data width,
not the user logic.

The vendor-neutral PHYs cover Xilinx, Lattice, Gowin, Efinix, Altera and Cologne Chip FPGAs, and the
BASE-X and BASE-R PHYs drive the transceivers without vendor Ethernet IP.

The core is small and configurable. The data width, the number of ARP entries, the FIFO depths, the
MTU and the clock domains are parameters, so a design pays only for what it uses.

When a CPU is present, the MAC can serve it as a software MAC for the LiteX BIOS and Linux, alone or
next to the hardware stack in hybrid mode. The figure below shows the three ways of using the MAC.

![The three uses of the MAC. A software MAC hands frames to a CPU through SRAM slots; the hardware
stack serves user logic with no CPU; hybrid mode shares one PHY between both, the hardware stack
taking its own traffic and the CPU the rest.](intro_variants.svg)

Every block can be simulated. The repository holds Python models of the MAC, ARP, IP, ICMP, UDP,
Etherbone and the PHY, used by its test suite, and a Verilator simulation of a whole SoC can talk to
the host through a TAP interface ([Simulation and verification](#simulation)).

## Features at a glance {#intro-features}

| Area | Features |
|--------------------|------------------------------------------------------------------------|
| PHYs | 10BASE-T on FPGA I/Os; MII, RMII, GMII, RGMII to an external PHY; SGMII and 1000BASE-X on transceivers and LVDS I/Os, 2500BASE-X on transceivers; XGMII to an external PHY or hard IP; 5GBASE-R, 10GBASE-R and 25GBASE-R on transceivers; an adapter for the UltraScale+ 100G hard MAC |
| MAC | Preamble, CRC32, padding and inter-frame gap; 8 to 64-bit PHY datapaths, 8 to 512-bit core datapaths; crossbar, Wishbone (SRAM slots) or hybrid interface; jumbo frames |
| Stack | ARP with a small cache, IPv4 with netmask and gateway, ICMP echo, UDP with any number of ports, DHCP client, IGMPv2 membership reports |
| Frontends | Etherbone master and slave (Wishbone over UDP), UDP streamer, raw UDP ports, AXI-Stream adapter for hardware MACs |
| Time | PTP (IEEE 1588-2008) slave over UDP/IPv4, E2E and P2P delay, hardware clock with a servo |
| Integration | LiteX library (`add_ethernet`, `add_etherbone`), or standalone Verilog core from `liteeth_gen` with a Wishbone, AXI-Lite or UDP interface |
| Host tools | `litex_server --udp`, Etherbone test scripts, a Wireshark dissector for Etherbone |
| Verification | Unit tests with Python models of every layer, RTL tests with Icarus Verilog and Verilator, PHY snapshot tests |

## Supported PHYs and FPGAs {#intro-phys}

The table below lists the PHYs, their line rate, the FPGA families they run on and their state.
[Supported FPGAs and boards](#boards) gives the boards; [MII, RMII, GMII, RGMII, XGMII and
10BASE-T](#parallel-phys), [1000BASE-X, 2500BASE-X and SGMII](#basex-phys) and [5G, 10G and 25G
BASE-R, and 100G](#baser-phys) give the details of each PHY.

| PHY | Line rate | FPGA families | State |
|----------------|------------------|-------------------------------------------|------------------|
| 10BASE-T | 10 Mbps | Any, on I/Os | Experimental |
| MII, RMII | 10, 100 Mbps | Any | Validated |
| GMII | 1 Gbps | Spartan-6, 7-Series | Validated |
| RGMII | 1 Gbps | Spartan-6, 7-Series, UltraScale, UltraScale+, ECP5, GW5A, Trion | Validated |
| RGMII | 1 Gbps | Agilex, Titanium | Build-tested |
| SGMII, 1000BASE-X | 1.25 Gbps | 7-Series, UltraScale, UltraScale+ transceivers and LVDS I/Os, GW5A | Validated |
| 1000BASE-X | 1.25 Gbps | Titanium LVDS, GateMate | Build-tested |
| 2500BASE-X | 3.125 Gbps | 7-Series, UltraScale, UltraScale+ | Validated |
| XGMII | 10 Gbps | Any, to an external PHY or hard IP | Not recorded |
| 5GBASE-R | 5.15625 Gbps | Kintex-7, UltraScale+ | Not recorded |
| 5GBASE-R | 5.15625 Gbps | Artix-7 | Build-tested |
| 10GBASE-R | 10.3125 Gbps | Kintex-7, UltraScale+, GW5A | Validated |
| 25GBASE-R | 25.78125 Gbps | UltraScale+ | In development |
| 100G (CMAC) | 4 x 25.78125 Gbps | UltraScale+ | In development |

The status words have one meaning in the whole manual, and the PHY chapters link here:

- *Validated* means validated on hardware: the PHY has carried traffic with a link partner on
  real boards.
- *Build-tested* means that the PHY elaborates and builds with the vendor toolchain, in a target or
  an example of this repository or of LiteX-Boards, and that no hardware result is recorded.
- *Not recorded* means that the repository records no hardware result for that combination.
- *Experimental* means that the code says so; no hardware result is recorded. The 10BASE-T PHY is
  experimental.
- *In development* means that the code or its notes say so: the PHY is incomplete and not ready
  for a design.

The BASE-R PHYs reuse the XGMII encoder of `LiteEthPHYXGMII` inside the FPGA, so that encoder runs
on hardware with every 10GBASE-R link. The XGMII row covers `LiteEthPHYXGMII` on its own pins, to
an external PHY chip or a hard IP, for which no board is recorded. The Kintex-7 and UltraScale+
5GBASE-R PHYs share their PCS and wrappers with the validated 10GBASE-R ones and differ by their PLL
settings; no hardware run at 5 Gbps is recorded for them.

7-Series covers Artix-7 (GTP), Kintex-7 (GTX) and Virtex-7 (GTH); UltraScale covers the Kintex
UltraScale GTH; UltraScale+ covers the GTH and GTY of the Kintex, Virtex and Zynq UltraScale+
families. LVDS means FPGA I/O pins with clock recovery in the fabric: the SelectIO pins of
UltraScale and UltraScale+ devices, and the LVDS pins of Titanium. GMII needs Xilinx clock buffers,
so it runs on the Xilinx families only. GW5A is the Gowin GW5AST-138, whose transceivers the BASE-X and BASE-R PHYs drive.

The RGMII PHY of the ECP5 can also read the link speed from the external PHY and follow a link
partner at 10 and 100 Mbps (`with_dynamic_link`); the other RGMII PHYs run at 1 Gbps.

The 10BASE-T PHY drives the twisted pairs from FPGA pins with a few resistors and capacitors. Its
source states that it is not an IEEE 802.3 compliant attachment, that it runs half-duplex only, and
that it is used at your own risk.

The photo below shows a small LiteEth board: the RGMII PHY of an ECP5 talks to the external PHY chip
of the RJ45 port, and Etherbone lets the host drive the FPGA registers over the network.

![A Colorlight 5A-75B board (Lattice ECP5) connected through its RJ45 port. The FPGA runs LiteEth
with the ECP5 RGMII PHY and Etherbone, and controls a relay module from the network.](colorlight_5a75b.jpg)

## What it is not {#intro-limits}

LiteEth is an Ethernet core for FPGA designs, not a general purpose network stack. It implements
what a design needs to move data and expose registers, and leaves out the rest:

- No TCP: the hardware stack carries UDP only. TCP needs a CPU running an operating system such
  as Linux behind the software MAC; the BIOS speaks UDP only (TFTP, DHCP).
- No IPv6 in the hardware stack. A CPU behind the software MAC can run it.
- No IP fragments: the IP layer sends unfragmented packets and drops received fragments. No IP
  options either: the received header must be 20 bytes long.
- No VLAN tags and no pause frames: the MAC neither inserts nor interprets them.
- No forward error correction and no autonegotiation or link training on the BASE-R PHYs: they
  run with FEC disabled at a fixed rate. The 2500BASE-X PHYs run the same autonegotiation as
  1000BASE-X.
- UDP checksums are not computed: the UDP layer sends a zero checksum, which IPv4 allows, and
  relies on the CRC of the frame.
- PTP is a slave clock only, over UDP/IPv4: no master or boundary clock, no Layer 2 transport.
- Etherbone is a subset of the protocol: 32-bit addresses and data, one record per frame, no
  address spaces.
- The MAC has no DMA: a CPU reads and writes frames in the SRAM slots of the software MAC.

The PHYs have their own limits, such as the speeds each one negotiates or the reference clocks it
accepts. Their chapters list them.

## Repository layout {#intro-layout}

| Path | Content |
|----------------------------------|-----------------------------------------------------------|
| `liteeth/mac/` | The MAC: preamble, CRC, padding, gap, SRAM slots, Wishbone and AXI-Stream interfaces |
| `liteeth/core/` | The hardware stack: ARP, IP, ICMP, UDP, DHCP, IGMP and PTP (`ptp/`) |
| `liteeth/frontend/` | Etherbone and the UDP streamer |
| `liteeth/phy/parallel/` | MII, RMII, GMII, RGMII (one file per FPGA family) and XGMII |
| `liteeth/phy/serial/` | 10BASE-T, the BASE-X PHYs (`basex/`), the BASE-R PHYs (`baser/`) and compatibility modules |
| `liteeth/phy/simulation/` | The PHY model of the LiteX simulator |
| `liteeth/gen.py` | The standalone generator `liteeth_gen` |
| `liteeth/software/` | The Wireshark dissector for Etherbone |
| `bench/` | Bench targets of about ten boards, simulation targets and host test scripts |
| `examples/` | Configuration files of the generator |
| `test/` | Unit and RTL tests, Python models of the protocols (`test/model/`) |
| `doc/` | This manual (`doc/manual/`), its figures (`doc/diagrams/`), photos and developer notes |

The network software of a LiteX SoC is not in this repository. The BIOS commands, the TFTP netboot
and the DHCP client in C are part of LiteX, in `litex/soc/software/` (the BIOS and `libliteeth/`),
and the Linux driver of the software MAC is part of the Linux kernel.
