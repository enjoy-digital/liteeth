# Preparing a hardware-MAC path for 100G

This implementation supplies a portable frame adapter, an initial UltraScale+
CMAC wrapper and reproducible simulation/synthesis benches. It has **not** been
tested on hardware and does not provide lossless 100G minimum-frame processing.
The selected vendor configuration is CAUI-4 NRZ without FEC, suitable for a
matching no-FEC optical module/peer. It is not a CR4/KR4/SR4 or PAM4 implementation.

## Ownership and interfaces

`LiteEthMACAXIStream` in `liteeth/mac/axis.py` adapts AXI frames to the normal
LiteEth PHY-facing stream. The frame starts at destination MAC and excludes
FCS. Byte lane zero is the first byte; `be` maps to `tkeep`. Non-final masks
must be full and final masks nonempty, contiguous from lane zero.

The adapter pads TX to 60 bytes using the existing padding inserter. The hardware
MAC owns FCS, preamble and IFG. Its PHY capabilities disable those soft-MAC
stages and the automatic PHY-side packet queues, since the adapter already owns
complete-frame TX and RX buffering. Explicit `with_store_and_forward=True`
remains available, but adds redundant queues.

TX commits a whole frame before exposing it to the hardware MAC and supports
AXI backpressure. Input errors are accumulated to final `tuser`, which requests
an errored transmission. The native producer must terminate frames within the
configured MTU; a never-ending or oversized TX packet is outside this contract.

RX cannot backpressure the wire. `PacketDropFIFO` commits only complete accepted
frames, dropping the entire frame on overflow, AXI error, malformed mask, runt
or oversize. It exposes 32-bit wrapping `rx_packets`, `rx_drops` and
`rx_bad_frames` counters in `eth_rx`; bad frames are a subset of drops, which
also include congestion. Boards must synchronize counter snapshots coherently
before exposing them to software. These counters cover AXI-delivered frames,
not every fault the vendor MAC may discard before that interface.

Endpoints belong to `eth_tx` and `eth_rx`. The parent owns clocks and resets.
When connecting `LiteEthUDPIPCore`, use its normal CDC and width conversion;
reset the connected domains together when flushing the complete pipeline.
The benchmark's reset test checks this coordinated reset, not arbitrary
one-sided FIFO resets or hot-plug recovery.

## Initial AMD wrapper

Import `USP_CMAC_100G` from
`liteeth.phy.serial.baser.wrappers.usp_cmac`. It instantiates an IP named
`liteeth_cmac` by default, with four differential GT lanes, a 161.1328125 MHz
reference, and a free-running 100 MHz initialization/DRP clock. The IP includes
GTs and shared reset/clock logic. Both MAC client domains use its 322.265625 MHz
TX user clock, as required by PG203; the recovered GT clock is not the RX AXI
clock. `link_up` is synchronized into `sys`; other raw status signals retain
their vendor clock domain.

The target generates the IP using `bench/cmac_100g.tcl`, after setting
`cmac_name`, `cmac_site` and `cmac_gt_group`. It owns pins, reference-buffer LOC,
CMAC/GT placement, clock/reset constraints, module management and peer mode.
The supplied IP template permits Ethernet frames up to 9022 bytes including
FCS. If changing the adapter MTU, keep the IP configuration consistent.

The wrapper enables reception and sends remote-fault indications until lanes
are aligned. It exposes underflow/overflow and alignment/fault signals for
bring-up. There is no AN, link training, RS-FEC, PTP or pause control in this
initial configuration, and no automatic standalone-generator entry: a board
must explicitly supply and constrain the IP.

Generate and synthesize with Vivado 2024.1:

```sh
PYTHONPATH=. python3 bench/cmac_100g.py --output-dir build/cmac_100g
cd build/cmac_100g
vivado -mode batch -source build.tcl
```

The default part is `xcvu3p-ffvc1517-2-e`; site and GT group are command-line
options. The build includes actual generated CMAC/GT RTL, not an empty stub.
The local synthesis resolved one CMACE4, four GTYE4_CHANNEL and one GTYE4_COMMON.
OOC DRC reports missing board pin/reference-buffer placement constraints as
expected. This is IP-interface/synthesis validation, not a placed board design
or a licensed bitstream qualification.

## Independent-clock traffic benchmark

```sh
PYTHONPATH=. python3 bench/mac_100g.py --profile standard --packets 128
PYTHONPATH=. python3 bench/mac_100g.py --profile minimum --packets 128
PYTHONPATH=. python3 bench/mac_100g.py --profile mixed --packets 64 --stall-cycles 200 --error-every 13 --reset
```

This Verilator benchmark uses a full UDP/IP core, finite queues and independently
scheduled system, TX and RX clocks. RX never waits for ready. A Python oracle
constructs headers/checksums independently; the RTL scoreboard checks bytes,
metadata, masks, ordering, stall stability, whole-frame losses and accounting.
It also requires TX to remain valid within each committed frame. RX errors,
application stalls, TX ready stalls and reset of unfinished frames are optional.

RX start times account for preamble, FCS and IFG at the offered rate; TX acceptance
is capped by a 100G wire-time model. This models the frame interface, not CMAC's
internal cycle-by-cycle scheduling, GT analog behavior or Ethernet block coding.
`--rate` sets offered RX rate only. `--sys-clk-freq`, `--rx-clk-freq`,
`--tx-clk-freq`, `--data-width` and `--fifo-depth` expose capacity tradeoffs.

Results report packet rate, wire-equivalent TX rate, delivered RX payload rate,
loss fraction, errors and maximum latency from RX frame completion. Finite
buffers can hide overload in short runs: use enough packets to reach steady
state and compare both loss and rate. The minimum profile is a 64-byte Ethernet
frame including FCS (18-byte UDP payload); standard and jumbo payloads are 1472
and 8972 bytes.

On the pre-optimization packet core, 512 bits at 250 MHz gave approximately
42 Gb/s minimum-frame TX; 128 offered minimum frames produced 33 whole-frame
RX drops. A 64-packet standard-frame run delivered all RX packets and about
96.7 Gb/s TX wire-equivalent throughput. The separate packet-start optimization
reduces minimum-frame overhead; it still does not sustain the 148.8 Mpacket/s
required for lossless minimum frames at 100G.

## Timing and regression

```sh
PYTHONPATH=. python3 -m bench.mac_100g_timing --output-dir build/mac_100g_timing
cd build/mac_100g_timing
vivado -mode batch -source timing.tcl
```

This routes the complete portable adapter/CDC/UDP path on the selected device
and reports resources, timing and CDC. It excludes CMAC/GT implementation and
board I/O delays. The clock-group exceptions isolate asynchronous domains;
they are not a substitute for a target's CDC constraints and review. The
reports establish internal register timing only. With the packet-start optimization
also applied, Vivado 2024.1 on `xcvu3p-ffvc1517-2-e` reported +0.067 ns worst
setup slack and +0.043 ns hold slack at 250 MHz system / 322.265625 MHz MAC clocks,
using 4463 LUTs, 8576 registers and 17.5 BRAM tiles. The small setup margin is not
board timing closure; regenerate these reports after integration or clock changes.

CI runs the adapter, padding, wrapper-elaboration and Verilator traffic tests
with the rest of LiteEth's MAC/core/frontend regression suite. Vivado builds
remain explicit local checks. Hardware validation must still cover the real
module/peer, reference clock and reset behavior, lane wiring, error recovery,
FCS/padding/IFG on the wire and sustained traffic.

Native PCS reference modelling remains separate from this frame adapter. AMD's
[RX clock requirements](https://docs.amd.com/r/en-US/pg203-cmac-usplus/RX-CLK),
[reset requirements](https://docs.amd.com/r/en-US/pg203-cmac-usplus/Resets), and
[AXI interface description](https://docs.amd.com/r/en-US/pg203-cmac-usplus/User-Side-AXI4-Stream-Interface)
are the vendor-interface references.
